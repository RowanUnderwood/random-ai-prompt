## False ComfyUI offline reports during image batches — 2.60.4-local.2

User supplied a screenshot showing the generation error "No selected ComfyUI instance is ready"
while the service panel showed both workers Ready. The generation path and panel share the
same probe, but run at different times: it queried `/system_stats` with a two-second timeout.
The installed ComfyUI implementation synchronously queries CUDA memory across all visible GPUs,
so transient latency was incorrectly interpreted as unavailable. The error remained visible
after the panel's later successful check.

Two regression tests failed on the old implementation: busy GPU-stat endpoint with a healthy
queue, and a valid readiness response delayed beyond two seconds. Changed the ComfyUI probe to
`/queue`, a ten-second response allowance, validation of both queue arrays, and shared in-flight
checks across UI/batch callers. Busy queues are valid. Added separate errors for ports that are
listening but fail readiness, so the UI does not direct users to launch duplicates.

Added ten regression cases covering busy queues, slow replies, unrelated services, concurrent
probes, active rendering, transient HTTP failure, fallback expiry, listener closure, incompatible
responses, and the listening-but-not-ready diagnostic. Rebuilt the portable update without closing
the user's app: a locked executable is staged as `.next.exe` and applied by `launch-desktop.bat`
after the old app closes. The running data/settings/images are preserved.

The initial live stress run completed four images but exposed three false readiness results even
with a ten-second queue probe. Added active-render tracking: a verified worker remains ready
while its TCP listener and admitted render are alive. For other clients' work, a recent validated
response covers transient HTTP failures for 60 seconds. Closed ports and incompatible responses
invalidate readiness immediately; cold startup is never accepted without validation.

Final live repeat: four independent image requests completed, divided across 3090/4090; all 302
readiness samples stayed ready, maximum probe 21 ms. The user's original app and services were
left running. Updated executable is staged as `.next.exe`; close the old app and relaunch with
`launch-desktop.bat` to activate the fix without moving settings or images.

Full gate: 397 Node + 433 web + 122 mobile tests (952 total). Production UI/native update builds
passed; the builder exercised the locked-executable staging path against the running app.
